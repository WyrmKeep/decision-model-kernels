------------------------------------------

Sequence of every run (kvwin_client.py, one keep-alive connection, sequential): 2 warm-up requests (check03, triage09; not compared), T1 = long00-storage on a nearly fresh pool, 6 other
long cases (long01..long06), T2, T3, T4 = long00-storage again: 11 long requests. Every request has a unique Ref: <10 digits> first line. Digits only: llama-tokenize (CPU, mix8 model,

3. What "window seen" and "window needed" mean (source facts, llama.cpp b12004)
-------------------------------------------------------------------------------

* Window seen = n_kv of the pass as the kernel gets it. llama_kv_cache::get_n_kv (src/llama-kv-cache.cpp:1256-1270) returns max(256, PAD(cells.used_max_p1(), 256)) over the streams of the ubatch:
  the highest used cell index of the stream plus one, padded to 256. With --kv-unified there is one stream shared by all slots, so the window is set by the highest cell of any sequence in the pool, also the
  cells of idle or finished slots. In the traces it is n_kv_padded = KQ-mask host-to-device copy bytes / (2 x n_tokens) (harness/profile/census/trace_census.py), only derived when the bytes are an exact multiple.
* Window needed = the request's own sequence padded to 256: pad256(max(start + n)) over its passes (census_lib.attn_cost). leadlib.pass_windows also gives needed_pool (own cells compacted at the
  front of the pool) and eff_front (mean cells a query tile reads when the own cells are at the front, see below).
* Why the stale cells widen the window [INFERENCE for the exact placement; the old traces show windows of 5,376-6,912 cells for sequences of 2,048-3,584 tokens and suffix windows smaller than prefix windows]:
  find_slot (non-contiguous) takes the first free cells from v_heads; the previous request of a slot keeps its cells after release ("stop processing: n_tokens = N"); a child's old cells are removed only in
  copy_prompt_to (tools/server/server-context.cpp:845-856: seq_rm(other.id, -1, -1) then seq_cp), after the parent has finished the prefix. So the parent's new prefix cells land behind the stale cells, and its own cells stay at
  high indices afterwards.
* What the FA kernel does with the window (ggml/src/ggml-cuda/fattn-common.cuh:1117): scan_mask = !use_sparse && mask && K->ne[1] % 256 == 0 && (Q->ne[1] >= 1024 || Q->ne[3] > 1). With --kv-unified
  Q->ne[3] = 1, so passes with N < 1024 tokens read the whole window (observed: the 908-token pass of the old long trace has no flash_attn_mask_to_KV_max kernel, trace-notes of the census, line 88);
  passes with N >= 1024 skip all-masked tail blocks (kb0_stop) but not interior blocks, which is exactly the stale-cell case of #28495.
* --no-kv-unified: n_stream = 3, one stream per slot, n_ctx_slot = 5,461, used_max_p1 per stream: the window of a sequence is its own cells. The cost moves elsewhere: seq_cp of the shared prefix to a child
  copies the whole stream buffer (about 179 MB per child over the 8 attention layers [INFERENCE: computed from the K/V sizes]) after llama_synchronize (llama_kv_cache::update), so expect an extra sync group per child
  request and device-to-device copies; with n_stream > 1 the mask scan is on for every pass. Observe it in Table T1/T2 (sync groups) and in the nokvu nsys run.
* Pass structure depends on the cache mode (from source, checked by the census and by analyze_childpass.py): src/llama-memory-hybrid.cpp:83-90 splits every batch with split_equal(n_ubatch, !unified).
  With --kv-unified (production) sequential = false: every ubatch takes all sequences with unused tokens. With --no-kv-unified (n_stream > 1, unified = false) sequential = true: only sequences with consecutive ids.
  The census default (census_lib.SPLIT_SEQUENTIAL = False, simulate_request(sequential=None)) is the unified split, so the reference prediction of both decisions of analyze_childpass.py is correct for production and for the
  two --kv-unified timing runs; the two --no-kv-unified runs are expected to follow the sequential split. For 3-question requests the two never differ; for 2-question requests they differ for the placement (0,2) only:
  sequential gives separate ubatches 120 + 51, unified gives 2 x 51 + 69. The 12 traced short requests are placements (1,0), (2,0), (2,1) and cannot discriminate. analyze_childpass.py tests both models for every request and reports
  "census (unified split) exact" and "sequential-split model exact"; its Table 1b reads kv_unified = '...' from the load_model line of each log and counts the requests the expected model reproduces [INFERENCE for the --no-kv-unified expectation: source only, not yet observed].
* Slot choice (get_available_slot): by LCP similarity if f_sim > 0.1, else least recently used. A long request with a new Ref shares only the header with the cached sequences (similarity < 0.1): LRU. Short prompts can hit
  LCP similarity (0.19, a server log of the data set data/2026-10-30-window1). id_slot is not supported by /v1/systemone, so the placement of T2 is not controllable: it is read from the slot lines.

The labels Z / Y / X1 of the spec are not defined in any census file. Pass structures are printed as census structure strings: P<n> prefix pass of n tokens, S<k>x<t> suffix pass of k sequences with t tokens each,
F<n> whole prompt in one pass (example: P2048+P1173+S3x43+S2x4+S1x26).

5. How to read the decision lines
---------------------------------

Rule: an effect counts if it is larger than 2 x the run-to-run spread. Spread = relative standard deviation (stdev / mean) of repeated identical measurements, floor 2 %: from the repeated T phases of the run
when they have equal windows, else from identical passes of the old traces (FA 4.5 %, GPU busy 4.4 %, 3 groups of the short trace).

| Line | Effect measured | Spread from | Yes means |
|---|---|---|---|
| window effect on the FA kernel | nsys: mean over T2..Tn of (FA ms of the passes with the same index and N as in T1) / T1 - 1; old traces: largest FA ratio of passes of equal kind and N with different windows | T2..Tn repeats with equal windows, else old traces | the FA kernel time follows the window |
| window effect on pass time | timing run: (sum of sync since_first_submit_us / serial roofline floor of the pass structure) of Tk over T1 - 1 (the floor ratio removes pass-structure differences of the slot placement); nsys run: GPU busy of the aligned passes; old traces: possible gain as share of GPU busy | as above | an exact window would shorten the pass time by more than noise |

The last two lines of the report are the consolidated answer: the FA line from the nsys run (else old traces), the pass-time line from the kv-unified timing run (else nsys, else old traces); the source is printed. The
per-source lines above them show disagreements. Typical readings: FA yes and pass time no = the kernel gets slower but the request does not measurably; both yes = the workaround is worth testing: compare
[timing:nokvu] (no) and Table T2 (nokvu / kvu GPU-side time, sync groups, pass structure).
The analyze_childpass.py decisions are counts, not timings (one request is evidence): "does any request type get more passes (ubatches) than the census predicts" compares DMK_TIMING ubatch lines per request with
census_lib.simulate_request (default split = unified) for the observed slot placement (the count is the same for the sequential split; the sizes are not); "does #30779 add a decode call / change pass sizes" compares the decode lines with the fixed order (parent slot lowest id, all children in the parent's suffix batch).
Which counter answers which question: ubatch line = model pass, decode line = llama_decode call = one update_slots() iteration; an "extra decode pass" in the PR text is an extra call, which need not add a ubatch.

8. Risks
--------

* Slot LRU decides where the target lands. T1..T4 can sit in different slots and have different placements (3-question requests: 6 permutations), hence different suffix passes. The tables print the placement and the
  structure per request; the timing decision divides by the roofline floor of the structure and the nsys comparison pairs only passes with equal index and N. A placement-matched comparison needs repeats (--repeat-target).
* T2 may not sit behind stale cells. Whether the window grows depends on where find_slot puts the cells; the report shows the observed window (seen / needed per pass) instead of assuming it. If T2 shows seen close
  to needed, the answer is no for this sequence, not for every sequence.
* T1 is not perfectly fresh: the two warm-up requests leave about 400 cells (the planted +256 of the synthetic data), and first-use costs (lazy module loads) land in the T1 wall time but not in kernel durations
  (column module_load_ms is printed).
* No window in the timing runs. n_kv is not logged by DMK_TIMING; the timing runs show the cost, the nsys runs the cause. The two runs are separate server runs: the placements can differ between them.
* Spread. With 3-4 target requests per run the spread is estimated from at most 2-3 repeats, else taken from the old traces (4.4-4.5 %). Effects of 2-4 % (the old-trace estimate for long requests) are at the edge of what one
  run resolves; --repeat-target adds repeats at 0.8 s each.
* nsys inflation: kernel times under nsys include profiler overhead [INFERENCE: about 3 % for long requests]; the ratios T2/T1 inside one run are not affected by a constant factor.
* FA model: the N = 73 passes lie above the global fit; for N >= 1024 the prediction at the needed window uses the cells a query tile reads with the own cells at the front (eff_front) calibrated by the closest pass (c_scan),
  a lower bound of the gain.
* --no-kv-unified also changes the split mode and adds seq_cp syncs/copies: the nokvu time can differ from the kv-unified time for reasons other than the window. Table T2 shows pass structure and sync groups side by side;
  the FA fit is not applied to the nokvu nsys run.
* Ref: length is neutralised by digit-only Refs (14 tokens always); the client prints a warning if the input_tokens of T1..T4 differ.
* Clock equality between the client and the server timestamps is an INFERENCE made before the first run; analyze_childpass.py prints the check (client send <= server start, server end <= client receive).
