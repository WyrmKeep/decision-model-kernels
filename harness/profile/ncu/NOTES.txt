Planned windows and estimates
-----------------------------

A window = -k regex:<partial regex on the function name> -s <skip> -c <count>; ncu counts only launches that match the filter, so a window
is robust against launches of other kernels before it. `python3 harness/profile/ncu/plan_ncu.py --md` prints three tables:
  - the pass structure of the first request on a fresh server and the cross-checks (mul_mat_q launches: model / census 245 / 245 for every pass
    with a matmul layer; stream-k fix-ups 64 / 127 / 183; MMVQ 0 / 3 / 248; all equal for the 13 traced passes);
  - the windows (run, request, passes, kernel filter, skip, count, first ... last kernel, nsys time of the window);
  - the estimates (per run and per file).
How the skips are known: the number of mul_mat_q launches of a pass (245, with 64 / 127 / 183 stream-k fix-ups) and of GDN / MMVQ launches does
not depend on N, or is predicted by census_lib and was checked against trace-passes.tsv for all 13 traced passes. A window that starts in a
later pass skips the matching launches of the earlier passes. The mul_mat_q filter also matches mul_mat_q_stream_k_fixup (a partial match on
purpose, the fix-up follows its matmul). Passes of the first requests that have no nsys trace (triage09 P1 with N=102, triage09 P2 with N=69,
check03 with N=158) take their kernel order from the neighbours N=94, N=73, N=120; the grid and J come from census_lib.

Estimates [INFERENCE] (the planner's output, ncu_cfg.COST): 13 runs, 147 profiled kernels; 4-ncu-smoke.txt 2 runs / 12 kernels, 0.9 to 2.6 min;
4-ncu-core.txt 6 runs / 81 kernels, 3.1 to 10.9 min; 4-ncu-extra.txt 5 runs / 54 kernels, 2.5 to 8.4 min; all 6.5 (optimistic) to 21.9
(pessimistic) minutes. seconds per run = run_fixed (optimistic 22 / pessimistic 55); seconds per kernel = t_save + passes x t_pass
(optimistic 0.3 + passes x 0.016, pessimistic 1.5 + passes x 0.10); passes = 25 (7 sections, [INFERENCE]) or 42 (--set full, measured on the
sample reports of the ncu install). Budget: 25 GPU-minutes in total (pessimistic), core at most 15. Order: smoke, core, extra (the slowest
last). The start/stop overhead is the run_fixed term (server start with the model load, ncu start, configuration of the first kernel, report
write, docker stop with up to 120 s timeout): 13 x 22 s = 4.8 min optimistic, 13 x 55 s = 11.9 min pessimistic, i.e. half of the pessimistic
total; every cut below is a run or a kernel that does not pay this again.
Example, core-long-p0 (13 kernels, std): optimistic 22 + 13 x (0.3 + 25 x 0.016) = 22 + 9.1 = 31 s = 0.5 min; pessimistic
55 + 13 x (1.5 + 25 x 0.10) = 55 + 52 = 107 s = 1.8 min.

What was cut (every cut class has a measured sibling or the nsys duration; cost it would have had [INFERENCE]):
  - attn_k / attn_v MMQ and the other attention-layer MMQ beyond extra-long-att: M=1024, 2 x 38 CTAs + fix-up, about 1.3 ms of a 420 ms
    N=2048 pass; same J, type, grid as the profiled ones. 1 run, 0.5-1.8 min.
  - tiny kernels: scale_f32, k_get_rows_float(_vec), cpy_scalar with 384 blocks, k_bin_bcast with 1-256 blocks, unary_op_kernel, k_set_rows,
    mask_to_KV_max, flash-attn aux: 2-12 us each, 0.3 % of an N=2048 pass. 4-5 s per kernel pessimistic.
  - quantize_mmq / rms_norm / glu beyond one instance per variant (extra-long-ew): from the nsys durations they run at 370-413 GB/s, i.e. at
    the DRAM floor.
  - J=48 (N=43) and J=64 (N=51) classes: a fresh server's first request never produces them (the first request of each case batches
    3 x 43 = 129, 2 x 4, 26 and 2 x 51, 69); they need a warm server with another slot placement. 1 run each.
  - N=69 (triage09 P2, J=80, 1 tile column): same J=80 kernel as N=129 / N=158 with fewer tiles. 1 run.
  - layers 1..31 of each pass: a layer repeats; layer 0 of a pass is profiled, the census gives launches per layer. 31 x 0.7-4 s per kernel.
  - check03 beyond smoke-a / smoke-b: one pass of 3 matmul shapes at N=158. 1 run.
  - medium P1-P3: same N and shapes as long P2-P4 (129, 8, 26). 3 runs.
  - application replay: needs a deterministic application and a client that waits for the replays.
  - --set full beyond extra-long-full: 42 passes instead of 25 per kernel, +70 % per kernel.

Option choices and why
----------------------

All runs: ncu -o /runs/<name> --target-processes application-only --clock-control none --cache-control all --replay-mode kernel
--pipeline-boost-state dynamic --apply-rules no --section-folder /tools/nsight-compute-2026.3.1/sections --section ... --metrics ...
--kernel-name-base function -k regex:<filter> -s <skip> -c <count> --kill yes --forward-signals, followed by /opt/dmk/llama-server ... (the
harness appends the server command). Every line has DMK_TOOL_CAPS=SYS_ADMIN (the harness `docker run --cap-add`) and DMK_STOP_TIMEOUT=120.

  entry point      the real binary /tools/nsight-compute-2026.3.1/target/linux-desktop-glibc_2_11_3-x64/ncu. The file
                   /tools/nsight-compute-2026.3.1/ncu is a 310-byte /bin/sh script ($APPDIR/target/.../ncu "$@" without exec, checked on the
                   host): as PID 1 of the container it would swallow the SIGTERM of `docker stop`, and --forward-signals would never see it.
  --clock-control none   required: the benchmark runs at the card's normal boost clocks; locking to base clocks would make every duration longer
                   than nsys and than production. The SM clock of each kernel is recorded (gpc__cycles_elapsed.avg.per_second, column
                   sm_clock_mhz), so a clock that differs between kernels is visible.
  --cache-control all (default)   caches flushed before every replay pass. Decided: every pass of one kernel starts cold, so the counters of
                   different passes belong to the same state. The weights (22 MB to 675 MB per kernel) are far larger than the 4 MiB L2, so
                   their DRAM bytes are the same as in production. Activations that stay in L2 in production (the q8_1 input, 5.9 MB at
                   N=2048 and less) read as DRAM bytes here: DRAM bytes of ncu are an upper bound for them. `none` would mix a cold first
                   pass with warm later passes inside one kernel's metric set and overstate hit rates [INFERENCE for the size of the effect].
  --replay-mode kernel   default: saves and restores the device memory the kernel writes, so in-place kernels (GDN state, KV cache, output
                   buffers) are replayed correctly; application replay needs a deterministic application and several runs.
  --pipeline-boost-state dynamic   not the default `stable`: the driver chooses the boost state as in production [INFERENCE: on this consumer
                   card both may be equal].
  --apply-rules no no guidance text in the report; all numbers are metrics. Smaller report and faster.
  --target-processes application-only   the profiled process is the server; no child processes are expected from llama-server [INFERENCE].
  --kernel-name-base function, -k regex:   partial regex on the function name: -k regex: is a partial match, so plain substrings joined by |
                   are enough (no ^ $ ( ) ? * [ which the harness's unquoted word splitting must not see). -s / -c count only launches that
                   match the filter.
  --section-folder /tools/.../sections   the sections of the tool directory (56 files, same 2026.3.1 as the local ncu).
  --kill yes --forward-signals   --kill yes ends the server after the last kernel of the window (the client sees a reset: outcome
                   server-killed); --forward-signals passes docker stop's SIGTERM to the server. The client waits until the port is refused
                   three times in a row, so the report is written before the harness's teardown.
  --metrics        7 extra metrics, see below. ncu aborts if one of them cannot be collected; the smoke runs show this first.

Source: ncu_cfg.py, plan_ncu.py (wrap_of), `ncu --help` of 2026.3.1, the scripts of the harness (start_server.sh, run_client.sh).

Section set (7): SpeedOfLight, LaunchStats, Occupancy, ComputeWorkloadAnalysis, MemoryWorkloadAnalysis, WarpStateStats, SchedulerStats (the

Running the analysis
--------------------

The schedule run copies runs/<name>.* (.ncu-rep or .ncu-repz, .client.json, .server.log) to its results directory; the reports of the
profiling window are compressed (.ncu-repz) and every tool of this folder reads both extensions. Then, with a local ncu command line tool of
the same release ($DMK_NCU, else ncu on PATH; --ncu PATH to change):

  python3 harness/profile/ncu/analyze_ncu.py <results dir> --out-dir <out dir>      # every .ncu-rep / .ncu-repz in the directory
  python3 harness/profile/ncu/analyze_ncu.py <results dir>/p3-ncu-core-long-p0.ncu-repz   # one report -> <results dir>/analysis/
  python3 harness/profile/ncu/analyze_ncu.py <results of smoke> <results of core> <results of extra> --out-dir <out dir>   # several directories
  python3 harness/profile/ncu/analyze_ncu.py --self-test                                # parser, units, alignment, speed of light (about 7 s)

Each report goes through `ncu --import <rep> --csv --page raw --print-kernel-base demangled` into a temporary file (HOME in a temporary
directory: ncu would create ~/Documents/NVIDIA Nsight Compute otherwise). Units are the ncu defaults (auto-scaled, 6 decimals) and are
converted to ns / byte / Hz; the same parser reads --print-units base output (tested). The run name is the file name; plan/<run>.json gives
the window.

  kernels.tsv     one row per profiled launch: class, window label, alignment, grid, block, duration, nsys duration of the same kernel, SM clock
                  and cycles, DRAM read / write / GB/s / % of 422 GB/s, L2 and L1 hit, IMMA / HMMA pipe %, executed int8 ops, issue %, SM
                  throughput %, achieved and theoretical warps, registers, smem, waves, occupancy limits, replay passes, stall shares. Headers
                  carry units.
  classes.tsv     the same columns averaged per (run, class), with min / max duration.
  sol.tsv, sol.txt   speed of light per class (below); sol.txt is Markdown table syntax in a plain file.
  alignment.tsv   per run: planned launches, profiled launches, matching launches, shift, status.
The columns of the four tables, with unit and meaning, are in COLUMNS.tsv next to this file. The header cells of kernels.tsv, classes.tsv and
sol.tsv carry a bracket text, for example `duration_us [duration, us]`; COLUMNS.tsv lists the name before the bracket. Per launch, the column
`align` of kernels.tsv is the alignment status of the run when the launch matches a planned launch, `unplanned` when it matches none
(`window` is then empty and `class` is named from the kernel name and grid).

How to read sol.txt
-------------------

1. Alignment of the windows. Statuses: ALIGNED (all launches are the planned kernels in the planned order), PARTIAL (the window ended early or a
   few launches differ), SHIFTED by +s (the window began s launches of the filter stream later than planned: run
   `plan_ncu.py --shift <KEY>=<value shown> --write` and rerun that line), MISALIGNED (classes are then named from the kernel names and have no
   model floor; do not read the speed-of-light rows), EMPTY (no launches; -s was larger than the stream or the server died first).
2. Planned vs hit classes. The count of launches per class that the plan expected against what the report holds; DIFFERS on any row means the
   window was not the planned one.
3. Speed of light per class. `time at the limit` = max over: model bytes / 422 GB/s, useful int8 ops / 149.3 TOP/s, fp16 flops / 38 TFLOP/s,
   fp32 flops / 18.1 TFLOP/s, 1.0 us launch floor; the largest is the `bound`. Model bytes = weights + q8_1 input + f32 output (matmuls) or the
   kernel's read + write bytes; kernels with no byte model use the measured DRAM bytes (stated in floor_source of sol.tsv).
   `% of limit` = time at the limit / measured duration. `gap per launch` = measured - time at the limit; `gap, ms per pass` = gap x launches of
   the class per pass (census); `share of the pass` = launches x measured / the GPU time of the traced pass (nsys). `nsys duration` next to
   `measured` shows the replay effect (cold caches, clocks). `DRAM % of 422 GB/s` and `useful int8 % of 149.3 TOP/s` say how far the kernel is
   from each limit; `IMMA pipe active` and the stall reasons say why (long_scoreboard = waiting for DRAM / L2, barrier / mio_throttle =
   shared-memory pipeline, wait = fixed-latency dependencies).
   `executed / useful int8 ops` (sm__ops_path_tensor_src_int8.sum over 2*M*N*K) next to `padded / useful ops expected from the tile grid` shows
   padding waste (N=158 on J=80 tiles: 1.013; N=129: 1.240). [INFERENCE: that the counter counts 2 ops per multiply-add as the census does;
   smoke-a checks it on the first mul_mat_q.]
4. Coverage of the passes. Per case and pass: the share of the traced pass that the profiled classes cover (launches x measured) and the gap to
   the limits of those classes. A class that is in two runs (std and full set) is counted once.

Not a bug: gdn_single has 32 CTAs on 38 SMs and a serial loop over chunks; its time at the DRAM limit is not reachable by this launch
structure, so its gap is a bound, not a target. concat_non_cont reaches 216 GB/s in the nsys trace; the floor in the table uses 422 GB/s,
while a plain copy reaches 408-411 GB/s (data set data/2026-10-30-card-limits, dram_copy), so up to 4 % of the gap of a copy-like kernel is not
reachable either.

After the smoke runs
--------------------

  ncu starts in the container, report written, server stops: check .server.log, that the .ncu-rep / .ncu-repz exists, and that .client.json has
      outcome server-killed and wall_ms_to_gone. If ncu fails with a permission error (ERR_NVGPUCTRPERM), the host driver restricts counters:
      this is not fixable by the schedule; stop and report.
  `answered` instead of `server-killed` in .client.json: the skip is larger than the stream: lower it with --shift.
  alignment of smoke-a and smoke-b (analyze_ncu.py output, alignment.tsv): ALIGNED on both: run core. SHIFTED: stray launches before the first
      request (a --no-warmup server should have none); apply the shown --shift to the filter keys with the same function; for a stray of another
      function nothing needs to change, the filtered windows count only their own function.
  regex with | reached ncu (smoke-b has 6 launches of MMVQ / quantize_q8_1): else the harness altered the words: stop.
  replay passes per kernel (column `passes` of kernels.tsv): 25 assumed: set ncu_cfg.COST['passes']['std'] to the measured value and rerun
      plan_ncu.py to get new estimates.
  time per kernel: (wall_ms_to_loss of .client.json - nsys time of the passes before the window) / kernels: set t_save and t_pass from this and
      the pass count; the planner reprints the estimates; run core only if it fits.
  int8_ops vs padded_ops (padded_over_useful vs padded_expected in sol.tsv): agree to a few percent: the counter reads as assumed.

Real reports
------------

The 13 reports of the profiling window (data set data/2026-10-31-profiles, folders raw/4-ncu-smoke, raw/4-ncu-core, raw/4-ncu-extra) were
analysed with analyze_ncu.py over the three folders: 147 profiled launches, 110 classes. Observed in that output:
  - replay passes per launch: 19 for the 139 launches of the 7-section set and 45 for the 8 launches of extra-long-full (--set full); the
    assumed 25 and 42 above were not replaced by these numbers in ncu_cfg.COST.
  - alignment.tsv: ALIGNED p3-ncu-smoke-b, core-long-p1, core-short-p0, core-short-p1, extra-long-full, extra-long-p4, extra-med-p0 (7 runs);
    SHIFTED p3-ncu-core-long-p2 (by -16 launches of the filter stream, hint: plan_ncu.py --shift L0=16, skip 825 -> 841; all 17 launches have
    align unplanned);
    MISALIGNED p3-ncu-smoke-a (2 of 6 launches match), core-long-p0 (1 of 13), core-mv (0 of 11), extra-long-att (1 of 13), extra-long-ew
    (0 of 9): in those runs the classes are named from the kernel names only and have no model floor (see "How to read sol.txt", item 1).
    Their speed-of-light rows are not to be read. The tool gives a rerun hint (--shift) only for the SHIFTED run; MISALIGNED runs give none.

Risks
-----

- Wrapper script: not used (real binary as entry point); a changed tool directory layout makes the path wrong, dry_run.sh does not see this.
- Stray kernels before the first request of a fresh --no-warmup server are not excluded; smoke-a shows them. Windows with a kernel filter are
  robust against strays of other functions.
- The demangled name format of ncu and the -k regex: behaviour on the `function` name base (namespace ggml_cuda_gated_delta_net_mma::) are
  checked only by the real reports above. The analysis reads the template arguments from the demangled name ((ggml_type)8, (int)128, ...);
  when only function names arrive it falls back to function + grid.
- Memory save / restore of 4.4 GB of device memory per kernel (--replay-mode kernel): 0.3-1.5 s per kernel [INFERENCE]; it dominates the cost of
  small kernels.
- The pass count of the 7-section set was assumed to be 25 [INFERENCE]; --set full = 42 was measured on the A4500 sample reports. The real
  reports show 19 and 45 (see above).
- Clocks: --clock-control none; the ncu duration can differ from the nsys duration by boost behaviour and by the cache flush; the SM clock is
  recorded per kernel.
- Report size: 13 reports of 6-17 kernels with 7 sections: small; --set full makes about 840 columns on the A4500 sample reports and is parsed
  in one call by `ncu --import`.
- Server log: ncu prints its per-kernel result into .server.log; the file stays small (at most 17 profiled launches per run).
- Untraced passes: N=102, N=69, N=158 have no nsys trace; their kernel order is inferred from the neighbours (N=94, N=73, N=120) and the grid
  and J come from census_lib; if the order is wrong the alignment shows it.
- --metrics aborts the run if a metric cannot be collected (all 7 names were checked against the ga104 metric list).
- ncu needs SYS_ADMIN in the container (the schedule sets it). Observed on the GPU host (read-only, /proc/driver/nvidia/params):
  RmProfilingAdminOnly: 1, i.e. counter access is restricted to users with CAP_SYS_ADMIN, which DMK_TOOL_CAPS=SYS_ADMIN grants to the
  container's root [INFERENCE: that a container capability counts for the driver's check; the usual NVIDIA-documented workaround is
  --cap-add=SYS_ADMIN]. The smoke run shows it; if it still fails with ERR_NVGPUCTRPERM nothing in the schedule can fix it (it would need a
  driver reload with NVreg_RestrictProfilingToAdminUsers=0). The 13 reports exist, so the counters were readable with the capability.
- In-place kernels (GDN state, KV writes) rely on kernel replay restoring memory; a wrong state would change a replayed kernel's behaviour but
  not its launch shape.
- sm__ops_path_tensor_src_int8.sum units are assumed to be 2 ops per multiply-add [INFERENCE].
- The launch floor of 1.0 us is the shortest kernel of the nsys passes (0.992 us); the floor of a launch-bound kernel is approximate.
