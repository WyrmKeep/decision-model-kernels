# Shape and launch census of the decision model (phase 3)

What every pass of every request type of the benchmark computes (matmul shapes, CUDA paths, FLOPs, bytes, roofline floors) and what the three old Nsight Systems traces show (launch counts, gaps), with a cross-check of the two. Model: H2O Lightning 4B mix8 on llama.cpp b12004 (commit 3c809f4), RTX 3060 Ti (sm_86, 38 SMs). Nothing here runs on the GPU: the scripts run on the CPU (python3 stdlib, `uv run` only for step 2) and read the header of the model file, the tokenizer and the three old captures.

All tables: units are in the column headers, one quantity per column, the source is under the table. Values that no source or trace shows are marked [INFERENCE]. `make_tables.sh` of the data set writes this report from the tables in `raw/`.

## 1 Key results

- **Cross-check**: the analytic model predicts the launch count of every kernel class per pass in all 72 traced passes and, for the 37 passes that have a launch listing, every one of the 9,119 matmul launches (weight type, tile width, need_check, grid.x, fix-up kernel) exactly. 11 of 12 checks pass without exception; the exception is the flash-attention K/V window (section 9, item 5).
- **Passes per request** (ref variant, with the `Ref:` line): short one-question 1, short two-question 3, medium 4, long 5. The question suffixes are *not* always batched by length: which sequences share a pass depends on the slots of the parent and the children (section 3.2); the pass count is the same for every slot placement, the pass sizes are not.
- **Every pass streams almost the same weights**: 3.34 GB for a pass with the output head, 2.62 GB without (prefix passes), 7.44 ms and 5.85 ms at 448 GB/s. A request is therefore 7.4 / 20.7 / 28.2 / 34.0 ms of weight reads (short-1q / short-2q / medium / long); the int8 compute floor is 7.3 / 11.4 / 68.6 / 161.5 ms at 144.8 TOPS (medium and long requests are bound by int8 work, short requests by weight reads).
- **MMQ is the only prompt matmul path** for Q4_0 and Q8_0 once a pass has more than 8 tokens; a pass of at most 8 tokens (4 tokens of one sequence, 2 x 4 tokens of two) runs *all* matmuls as MMVQ. cuBLAS is never used. 245 MMQ launches per pass, plus 3 MMVQ launches (fused FFN of the last layer on the output rows, output head) when the pass has an output.
- **The output head is computed for 248,320 rows per output; the API reads 2-8 of them** (section 6.3): 0.68 GB (one head read) per one-question request, 2.03 GB per medium or long request (three head reads).
- **Traces vs floor** (nsys overhead not removed): the GPU-busy time of a pass is 1.6x (pass of at most 8 tokens) to 4.3x (prefix passes) the larger of the weight and int8 floors and 1.4x to 2.1x the serial per-kernel roofline floor (section 8.2); the MMQ kernels reach 31-53 int8 TOPS (22-37 % of 144.8; 31 TOPS in the suffix passes, 53 TOPS in the large prefix passes) and the all-MMVQ pass reads weights at 365 GB/s (81 % of 448) (section 8.3). In-pass launch gaps are 0.20-0.35 % of a long or medium prefix pass and 3.3-5.3 % of a suffix pass (section 7).

### 3.2 How a request becomes passes

The server (`tools/server/server-context.cpp`, `server-decision.cpp`, `src/llama-batch.cpp` `split_equal`) turns a request into passes by these rules (all read from the b12004 source, then confirmed by 20 traced requests):

1. A request with one question has no sharing: one pass with the whole prompt (split at 2048 tokens), output on its last token.
2. A request with 2-3 questions is a parent task (question 0) plus child tasks that run in other slots (`-np 3`). The parent evaluates the shared prefix alone in ubatches of at most 2048 tokens (no outputs; the last layer's FFN and the output head are empty and are skipped).
3. When the prefix is done the parent starts the children. In the same `update_slots()` loop the children whose slot index is *above* the parent's are visited after it, so their suffix is in the same `llama_decode` batch as the parent's suffix; children with a *lower* slot index were visited before and follow in the next batch (one extra iteration).
4. Every batch is split by `split_equal(n_ubatch, sequential)`; the hybrid memory passes `sequential = !unified` (`src/llama-memory-hybrid.cpp` lines 83-90), and production runs `--kv-unified`, so `sequential = false`: a ubatch takes the first sequence with unused tokens and then every other sequence with unused tokens, each with min(remaining) tokens (so a sequence in slot 0 and one in slot 2 share a pass); a sequence that finishes in a ubatch gets an output row. [Correction: the first version of this census used `sequential = true`, the setting of the pure recurrent memory, which only lets consecutive seq ids share a pass. The 20 traced requests are reproduced by both settings; they differ only for a two-question request in slots (0, 2). `census_lib.SPLIT_SEQUENTIAL` selects the setting; the DMK_TIMING `ubatch` lines (n_seqs) of a request with the child in a higher slot than the parent decide it on the running server.]
5. Slot placement is decided by the server (least recently used among idle slots), not by the benchmark. All six placements of 2 or 3 questions on 3 slots are enumerated by `census_lib.arrangements()`.

## 4 Matmul shapes and the kernels they hit

Rules (`ggml/src/ggml-cuda/ggml-cuda.cu` `ggml_cuda_mul_mat`, `mmq.cu/cuh`, `mmvq.cu`, `mmq-config-ampere.cuh`; every one reproduced by the traces): Q4_0/Q8_0 weights with N <= 8 columns use `mul_mat_vec_q` (MMVQ), otherwise `mul_mat_q` (MMQ, stream-k, 128-row tiles, 256 threads, tile width J chosen as the smallest of {8,16,24,32,40,48,64,80,96,112,128} (fallback tiles for M % 128 != 0: {8,16,32,64,128}) that gives the fewest column tiles); stream-k grid.x = number of tiles if the tile efficiency is >= 90 %, else min(38, work units) with a fix-up kernel when tiles % grid.x != 0. Every matmul has its own activation quantize kernel (`quantize_mmq_q8_1` or `quantize_q8_1`); there is no gate/up fusion for MMQ with Q4_0, so up and gate are two launches. MMVQ with N = 1 fuses gate+up+SwiGLU and down+residual add (`mul_mat_vec_q<Q4_0,1,fusion>`).

## 9 Discrepancies and corrections

Each item: what the first version of the model (or an earlier estimate) assumed, what the source or trace shows, and what the census now does.

1. **Passes are not formed by distinct suffix lengths alone.** First model: all active sequences with the same remaining length share a pass (3 x 43, then 2 x 4, then 1 x 26). Traces: that holds for 2 of 8 three-question requests; the others ran 43 + 2 x 47 + 26 or 2 x 43 + 4 + 73, and all 12 two-question requests ran 120 and 51 as separate passes. Cause: slot order in `update_slots()` (a child below the parent follows in the next batch; section 3.2) and `split_equal(sequential = false)` of the hybrid memory (the first version of the census assumed `sequential = true`; see 3.2 rule 4). Census: `simulate_request()` over all slot placements; the pass count per request is the same in every placement, the N of the passes differs, and the all-MMVQ pass (N <= 8) exists only in the structure 3 x 43 + 2 x 4 + 26.
2. **The last layer's FFN at one output row is two fused MMVQ launches, not three.** First model: up, gate, down. Trace: `mul_mat_vec_q<Q4_0,1,fusion>` grid 9,216 (gate+up+SwiGLU) and grid 2,560 (down + residual add); a pass with an output therefore has 245 MMQ + 3 MMVQ (fused up/gate, fused down, head) = 248 matmul launches, and 248 MMVQ in an N <= 8 pass. Fixed in `pass_matmuls()`.
3. **A second Gated DeltaNet kernel.** First model: only `gated_delta_net_cuda`. Trace: `gdn_single<16,128,1>` (tensor-core chunk kernel, grid 32 x S x 1) in every pass with >= 64 tokens per sequence (all prefix passes, 73- and 120-token suffix passes); the 4/26/43/51-token passes (also 2 x 43 tokens) use the recurrent kernel. Fixed in `gdn_cost()`.
4. **Graph order is not creation order.** The census-sequence order (qwen35.cpp node order) does not match the launch order in the trace (for example ssm_beta/ssm_alpha follow attn_qkv, attn_gate follows the delta-net). The cross-check compares multisets per pass; `census-sequence.tsv` is a list of the matmuls of a pass, not a schedule.
5. **The flash-attention K/V window is wider than the request's own cells.** First model: n_kv = the highest position of the request, padded to 256. Trace (derived from the mask copy): equal in 33 of 72 passes, larger in the rest by up to 5.0x (for example 5,376 cells for a 2,048-token prefix pass); never smaller. [INFERENCE] cause: cells of idle slots stay in the unified cache. Not corrected in the model (needs the slot history). Effect: the attention FLOPs and the attention mask (N x n_kv x 2 B per pass, host to device) are larger than modelled for those passes; whether the flash-attention kernel time grows with the window was not measured.
6. **Recurrent-state copies.** The model assumes the gather of S states plus a write-back per layer (get_rows grid.x = S in all passes, confirmed). The three 86-token suffix passes (2 sequences x 43 tokens, structure 2 + 1 + 1) additionally contain 48 device-to-device copies of 2.2 MB (about 1 ms per pass, column `d2d_gpu_in_pass_ms` of `trace-passes.tsv`); [INFERENCE] the third sequence's recurrent cell lies between the two used cells and is copied as well. Not in the model.
7. **Kernel counts per pass.** An earlier estimate was about 1,280 launches per pass; the traces show 1,065-1,296 (1,166 for 2,048-token prefix passes; 1,248 or 1,296 for suffix passes with the MMQ path; 1,065 for N <= 8). 245 MMQ launches per pass is exact. The census counts only matmul, quantize, flash-attention and GDN launches (the rest is in `trace-kernels.tsv`).
8. **Main MMQ grid.x is not always 38.** It is the tile count when the tile efficiency is >= 90 % (for example 1,024 and 72) and 38 or 10 with a fix-up kernel otherwise; the model predicts every observed value (Table 5, `crosscheck-keys.tsv` is empty).
9. **Token counts**: the sum of the question prompts per request (what the API counts) matches the production run exactly for the raw variant (Table 3). The traced short requests use a random `Ref:` value, so their prefix length varies by a few tokens; the cross-check takes the observed prefix length and the plan's suffix lengths.
10. **Not verifiable here**: the nsys overhead (3 % long, 25 % short, earlier estimate), the frequency of the slot placements in production, and the cause of the wider K/V window (item 5). No untraced measurement was made.

## 10 Limits, GPU needs, files

**What needs the GPU**: nothing. All steps (`run_all.sh`) run on the CPU: steps 1 and 2 need the model file and the tokenizer, the trace step needs the three captures, steps 3 to 5 need only the data set. For phase 3 the model gives measurement targets that do need the GPU (not run here): the time per kernel class at the N values of Table 7, the pass time for N <= 8 against the 7.44 ms weight floor, and the slot placement distribution of a production-like request stream.

**Assumptions of the analytic columns**: FLOPs are 2 x M x N x K per matmul (padded tile work is in `padded_gops`); weight bytes are the file sizes (34 / 18 bytes per 32 elements); floors use the nominal 448 GB/s and 144.8 int8 TOPS (1,861 MHz); the FP16 and FP32 peaks and the element-wise traffic per layer (`census_lib.side_ops`) are [INFERENCE]; the K/V window is the request's own cells (item 5).
