# Lead 30489: GLU in the quantization of the activation (result)

Written 2026-10-31, after the measurement window (00:02 to 01:14 UTC).

## Task of this entry

This entry gives the result of one measurement of pull request #30489 of llama.cpp. The pull request fuses GLU into the quantization of the activation in MMQ. We measured it as a lead. The project does not use it in production. The [README of the data set](../../data/2026-10-31-lead-30489/README.md) gives the raw files, the tables, and the conditions.

The method has a rule. We commit a prediction entry before the measurement. We did not write a prediction entry for this test.

We wrote the prediction in a file that is not in this repository, on 2026-10-30. The time of that file is 23:12 UTC. The first run started on 2026-10-31 at 00:47 UTC. The repository cannot show the date of that file. The section "Prediction against result" gives its text.

## Result in short

- The build with the patch (arm L) is faster than build D in the private benchmark. `lat_ms` is 1.94 % lower (95 % interval: -2.38 % to -1.50 %).
- The change is -2.25 % for the long request, -1.99 % for the medium request, and -1.23 % for the short request. The interval of the short request is -2.14 % to -0.34 %.
- The prompt speed of `llama bench` is +1.00 % at 64 tokens, +2.14 % at 256 tokens, and +2.31 % at 3,000 tokens. No interval includes 0.
- The answers of the 8 runs are the same bit for bit on all 100 decisions. The equivalence class `exact` holds for these decisions.
- 6,744 of the 6,748 names in the two builds have the same SASS. The 4 other names are kernels for a type that the model does not use.
- The speed increase is less than the ceiling of the prediction. It is 61 % to 77 % of the ceiling for the short request, the medium request, and the long request.
- The load of the host was high in blocks 2 to 4 and in all runs of `llama bench`. We did not control it.
- This is a lead. The project does not use it in production.

## Change in the pull request

In b12004, each feed-forward layer of "mix8" does four steps. [INFERENCE: this comes from the list of types of the MMQ fusion in b12004 and from the list of the kernels of one pass. The second list is not in this repository.]

1. Two MMQ kernels multiply the state by the weights `ffn_gate` and `ffn_up`.
2. The kernel `unary_gated_op_kernel` calculates SiLU of the `gate` result times the `up` result. It writes the F32 result.
3. The kernel `quantize_mmq_q8_1` reads that result and writes it as Q8_1.
4. One MMQ kernel multiplies the Q8_1 data by the weight `ffn_down`.

The patch removes step 2 when a GLU node gives its output to an MMQ matrix multiply. The matrix multiply of `ffn_down` runs at the position of the GLU node. Its quantization kernel reads the `gate` tensor and the `up` tensor. It calculates SiLU of `gate` times `up` in registers and quantizes the result. The program does not write the F32 result of the GLU and does not read it again.

The patch fuses only if all of these conditions are true. We read them in the function `ggml_cuda_should_fuse_glu_mmq` of the commit.

- The `gate` tensor, the `up` tensor, and the result are F32.
- The width of the GLU is a `multiple of 4`.
- The `gate` tensor and the `up` tensor are `contiguous` and `aligned` to 16 bytes.
- The usual selection gives MMQ and not MMVQ.
- The GLU operation is `SWIGLU`, `GEGLU`, `SWIGLU_OAI`, or `SWIGLU_CLAMP`.
- No other node uses the GLU output. No node between the two nodes changes the buffers.

A pass of 8 tokens or less uses MMVQ for each matrix multiply. The patch does not apply to it. The commit changes 6 files, with 531 added lines and 31 removed lines. The [README of the data set](../../data/2026-10-31-lead-30489/README.md) names the files and the commit. We did not change the code of the commit.

## Equivalence class

We selected the equivalence class `exact` before the measurement. [INFERENCE: the file that is not in this repository gives the equivalence class. The repository has no entry from before the measurement.] The fused kernel does the same operations in the same sequence and with the same precision as the two kernels that it replaces.

- The fused kernel uses the same operation `silu(gate) * up` as the kernel `unary_gated_op_kernel`.
- The program before the patch writes an F32 value and reads it again. This does not change the value.
- The value then goes into the same code for `amax`, for the sum, and for `roundf` of the Q8_1 data.

The equivalence class `exact` has one test. The answers of the build with the patch must be the same bit for bit as the answers of the build without it. The [method](../method.md) gives this test. The method shows a fusion of kernels as an example of the equivalence class `re-associated`.

This fusion does not change the sequence of the sums or the precision of one value. For this cause, we selected `exact`. If the answers are different, the tests of `re-associated` apply. We also compared the SASS.

## Host load and its effect

The host did other work during the schedule. The cause is not in the data.

### Facts

- The one-minute load average was 1.61 to 2.56 in block 1 of the private benchmark. It was 3.00 to 18.70 in blocks 2 to 4. It was 14.61 to 18.70 in the 8 runs of `llama bench`.
- In blocks 2 and 4, the load of the run of L is more than the load of the run of D. This is true before and after the run. In block 3, the load of the run of L is less before the run and more after the run.
- Arm L ran first in block 1 and second in blocks 2 to 4.
- `lat_ms` of arm D was 237.2 ms in block 1 and 242.1 to 242.8 ms in blocks 2 to 4. `lat_ms` of arm L was 232.0 ms in block 1 and 236.5 to 239.2 ms in blocks 2 to 4.
- The `lat_ms` ratio is -2.18 % in block 1. The mean of blocks 2 to 4 is -1.86 %. We calculated the mean from the table above.
- The first value of arm D is 237.2 ms at a load of 1.90 to 2.56. It is 0.1 % or less different from the values of arm D in the [result of phase 1](2026-10-30-phase1-equivalence-result.md) at a load of 2.13 to 2.84. Those values are 237.2 ms to 237.3 ms.
- The value `throttle_reasons_at_start` is `0x0000000000000024` for the two runs of block 4. The driver shows the power cap and the heat limit. The median SM clock is 1,860 MHz for D and 1,845 MHz for L.
- The `llama bench` speed of arm D is 0.3 % to 0.9 % less than in the result of phase 1, where the load was 2.08 to 2.62. We calculated this from the two entries.

### Meaning of the facts

- Each request is about 2 % slower at the higher load, for the two arms. [INFERENCE: this is the same as the effect in the result of phase 1. No test changed only the load.]
- The data do not show if the load changes the ratio. The one block with a low load gives a ratio that is 0.3 % lower than the mean of the other blocks. One block is not sufficient for more.
- In blocks 2 and 4, arm L ran at the higher load. If a high load makes requests slower, this makes the speed increase of L smaller. [INFERENCE: no test checked this.]
- In `llama bench`, arm L ran first in all blocks, and the load fell during the 8 runs. The test cannot find the effect of the arm and the effect of the sequence independently. [INFERENCE: we did not measure the effect of the sequence.]
- The load makes the interval less sure than it shows. The result is sufficient for a first look at the lead. It is not sufficient for a decision to use the lead.

## Prediction against result

- **Equivalence class:** `exact`, from the code and from the SASS.
- **Ceiling:** the time of the kernel for SwiGLU that the patch removes, less the time to read the second tensor in the quantization kernel. The file thinks that the quantization kernel waits for memory. It thinks that the kernel uses about 50 % of its time to read the second tensor. The ceiling is then about 2.0 % for the short request, 2.7 % for the medium request, and 2.9 % for the long request. The unit is the kernel time.
- **Dimensions that change most:** the speed at 3,000 tokens, the medium request, and the long request. A pass of a short request is small.
- **Source of the lead:** the author of the pull request measured +1.0 % to +1.8 % for the prompt speed on a 4090 GPU with Q4_K. No person measured Q4_0 on `sm_86`.

## Limits and next work

- This is a lead. The project has no change document for it, and production does not use it.
- The test has 4 blocks, one benchmark, and one GPU. The interval is small because the 4 blocks are near each other. It does not show the result for other tests.
- We did not control the load of the host. In `llama bench`, the sequence of the arms was the same in all blocks.
- The answers are the same on 100 decisions of one benchmark. The test does not show the other inputs.
- The data set does not show the same SASS for 5 of the 6 kernels `quantize_mmq_q8_1` with no fusion. The pair for the layout `D4` is one of them.
- We did not run `test-backend-ops` or `compute-sanitizer` on the build with the patch.
- This test did not lock the SM clock and did not measure the kernel only. The [method](../method.md) tells us to do this for a change to a kernel.
- This test did not use the sequence A, B, A of the [method](../method.md) for a change to a kernel.

Before the project uses the patch, it must do these steps.

1. Write a prediction entry and commit it before the measurement.
2. Run `test-backend-ops` for the GLU cases of the commit on the build with the patch.
3. Run the four tools of `compute-sanitizer` on the build with the patch.
4. Measure again at a low load, with more blocks and a different sequence of the arms in each block.
5. Make a profile of the two builds to find the time of the fused kernel.
6. Write a change document in `docs/changes/` with the equivalence class `exact`.

The same method can fuse a small kernel into the quantization of the activation in other pairs of kernels of the graph of "mix8". This entry does not measure it.
